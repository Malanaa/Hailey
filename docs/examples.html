Recipes and examples

Runnable patterns for classification, extraction, task composition, and local input.

Support ticket triage

This complete offline program combines a typed result, named context, branching, and a test. The mock value is deliberately explicit so the example runs without credentials.

// This example uses a fixed fixture. No network or API key is needed.
type Ticket {
  category: "billing" | "bug" | "question"
  urgency: "low" | "high"
  summary: String
}

model local {
  provider: "mock"
}

context policy {
  text: "Billing questions go to the accounts team. Outages are high urgency."
}

task classify(message: String) -> Ticket {
  model: local
  context: [policy]
  system: "Classify the support message using the policy."
  prompt: "Message: {{message}}"
  mock: {
    category: "billing"
    urgency: "low"
    summary: "Customer reports a duplicate charge."
  }
}

flow main {
  let ticket = classify("I was charged twice this month.")
  print ticket
  if ticket.category == "billing" {
    print "Route to accounts"
  } else {
    print "Route to support"
  }
}

test billing {
  let ticket = classify("I was charged twice this month.")
  assert ticket.category == "billing"
  assert ticket.urgency == "low"
}
hailey run examples/triage.hailey
hailey test examples/triage.hailey

Represent missing information

Nullable values let the workflow distinguish absent data from an invented placeholder. Here the result has no email address, so the workflow asks for one.

type Contact {
  name: String
  email: String?
  interests: String[]
}

model fixture {
  provider: "mock"
}

task extract(text: String) -> Contact {
  model: fixture
  system: "Extract the contact. Use null when the email is missing."
  prompt: "{{text}}"
  mock: {
    name: "Avery"
    email: null
    interests: ["language design", "AI"]
  }
}

flow main {
  let contact = extract("Avery works on language design and AI.")
  print contact
  if contact.email == null {
    print "Ask for an email before sending anything"
  }
}

test missing_email {
  let contact = extract("Avery works on language design and AI.")
  assert contact.email == null
}

Chain two tasks

Tasks can pass structured results to other tasks. Calls remain sequential. Each task consumes an attempt, and both results appear in the trace.

type Ticket { category: "billing" | "bug" }
model fixture { provider: "mock" }

task classify(message: String) -> Ticket {
  model: fixture
  prompt: "Classify {{message}}"
  mock: { category: "billing" }
}

task draft(ticket: Ticket) -> String {
  model: fixture
  prompt: "Draft a reply for {{ticket.category}}"
  mock: "We will review the duplicate charge."
}

flow main {
  let ticket = classify("I was charged twice.")
  let reply = draft(ticket)
  print reply
}

Bring a local file into a workflow

File reads require an explicit directory grant. You can pass the resulting String to a task parameter. Hailey records the content when tracing is enabled.

// File paths are relative to this source file.
// Run with --allow-read examples to grant access.
flow main {
  let policy = read_text("policy.txt")
  print policy
}
hailey run examples/files.hailey --allow-read examples

Take input from another application

flow main {
  let message = input("message")
  print message
}
hailey run echo.hailey --input "message=Hello from the shell"

For programmatic integration, the JavaScript API gives you structured output without parsing console text.

Move beyond fixture tests

Replace the mock model with a compatible provider and remove the mock property when you want actual inference. Use a set of representative messages, include ambiguous inputs, and review incorrect results. A passing fixture test proves workflow behavior for that fixture. It says nothing about the quality of a live model.

Hailey v0.1 provides assertion-based test blocks. Dataset loaders, statistical evaluation reports, prompt optimization, and model comparisons are future work. You can build those around the JavaScript API today.
